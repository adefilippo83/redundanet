Project talk

RedundaNet

Distributed, encrypted, very redundant storage, run by a community of volunteers, not a company.

Tahoe-LAFS · Tinc mesh VPN · GPG identities · a Git repo as the source of truth · Docker Compose · Raspberry Pis, old PCs, a €4 VPS

redundanet.com · github.com/adefilippo83/redundanet

Start with the one-liner: a storage network you join by opening a pull request, where your files survive any machine dying and nobody hosting them can read them. Then straight into the Cubbit story.

Where it came from: an orphaned idea

Very distributed (commodity hardware behind home NATs) · very redundant (erasure coding) · membership as a social process.

I backed the Cubbit Kickstarter in 2019 and I still have the box. When they pivoted to enterprise object storage I didn't blame them, it was the right business call. But it left the idea I cared about with nobody carrying it. A network the members run themselves can't pivot away from them. That's the whole reason this exists.

Six principles

🔒

Nobody can read your data

Encryption happens on your device. Hosts store ciphertext.

💥

Any node may die

Erasure coding, configurable k-of-n.

🗂️

No central authority

Identity = your GPG key. Membership = a file in Git.

🏠

Commodity, behind NAT

Home routers, no port forwarding. A mesh VPN relays.

🤝

Vetted, not anonymous

Members are approved humans. Some rules are an honor system, and we say so.

🧘

Boring operations

One CLI, one compose stack, self-update with rollback, a status page.

Dwell on "vetted, not anonymous". This is the trust model everything else leans on: members are approved humans, so some enforcement can be honor-system (quotas, later) and that's a deliberate choice, not naivety.

Architecture

Walk it left to right: the repo is the source of truth and nodes sync it; the keyservers are the PKI; two hubs. The rendezvous is a plain VPS because it has to see the clients' real addresses; fly sits behind a proxy and could not, which is the incident I tell later. Two introducers, either can be down. Every node runs the same stack on whatever hardware. Mention that the tinc container owns the network namespace and the Tahoe containers join it.

Why Tahoe-LAFS: the trust boundary

IPFS

public, popularity-based persistence

Ceph / MinIO

great for a trusted cluster you own

Storj / Sia

a token market, not a social contract

The criterion was the threat model, not the feature list. Untrusted hosts means encryption has to happen in the client, and that is Tahoe's entire thesis. Be upfront that upstream moves slowly: I chose it knowing that.

Connectivity & identity: Tinc + GPG

Why full fingerprints: a short key id is just the last 8 or 16 hex characters of the hash, and Evil32 showed you can forge one in seconds. Earlier versions accepted short ids and matched by suffix, so an attacker could upload a colliding key and become a node. Now rejected everywhere. Why tinc and not WireGuard: WireGuard is a tunnel, I needed a mesh with relaying and one identity; tinc gives both, I pay in throughput I don't need. One thing tinc taught me the hard way: it keeps the first address it learns for a peer, so a rendezvous behind a proxy poisons every node's address table. The rendezvous must be a host that sees real client IPs.

Inside a node: one compose stack, roles as profiles

docker compose -p redundanet --profile storage --profile client up -d · the Tahoe containers join tinc's namespace: no port plumbing, and one trap I'll show you.

The shared network namespace is elegant and it set a trap. Don't explain it here, just plant it.

Open the status page. Point at the census: it's built from each storage node's list of opaque storage indexes, no filenames, no content, served only over the VPN. If the census shows under-replicated objects, say why: after an encoding change every old file counts against the new target until the rebalancer converges it, and the page is the progress bar.

Redundancy that is measured, not assumed

The network started as a 1-of-2 mirror and moved to 2-of-4: same 2× cost, survives two nodes. The change is one line in the manifest; every node reads it, new uploads use it at once, and the rebalancer converts old files on its own.

Own the honesty point: the docs used to say 3-of-10 while production ran 1-of-2. I fixed the docs to say what we actually run. Claim what you run. Encoding is baked into each file at upload, so changing the manifest needed a re-encoder loop: it reads k and n straight out of the capability string and re-uploads from the grid itself. A weekly sweep also repairs any object that lost a share, from the surviving shares. Redundancy you never repair is a hope, not a property.
Live demo 2

Kill a node, keep the file

# node A (client): upload, note the hash
sha256sum talk.pdf
redundanet storage upload talk.pdf home:talk.pdf

# node B (storage): take it down
docker stop redundanet-tahoe-storage

# status page: one server fewer, census shows reduced availability
# node A: download still works from the remaining copy
redundanet storage download home:talk.pdf /tmp/back.pdf
sha256sum /tmp/back.pdf     # identical

docker start redundanet-tahoe-storage   # census returns to fully replicated
Have talk.pdf ready and the hash already noted. Stop the Pi's storage container, download from falcon, compare hashes. The client reconnects in seconds. Start the container again before moving on.
Challenges · production incidents

Fix the class, not the instance

The vanishing disk

An explicit -f compose.yml disables Docker's override auto-load; an update silently detached a 1TB disk. Fixed in the CLI, with a test asserting two -f flags.

Fresh-node breakage

The Pi image shipped Compose v1; a manifest typo broke a join for 11 minutes. Now: pinned Compose v2 verified at build time, actionable errors instead of tracebacks.

The rendezvous that lied

A packet capture showed every node-to-node byte crossing the hub over TCP. fly's proxy hid real addresses, and tinc keeps the first address it learns. Fix: a €4 VPS as rendezvous, one manifest line.

If short on time, tell the vanishing disk and the rendezvous. The disk: the command looked right, but an explicit -f turns off Docker's auto-loading of the override file, so an update silently detached a 1TB disk; the data was fine, the node just couldn't see it. The rendezvous: I assumed the mesh was a mesh. A capture on one node showed zero packets to any peer's real address: everything went to fly, over TCP, because fly's proxy showed the hub its own address as the source of every peer and tinc remembers the first address it learns. The lesson is on the last slide: the topology can lie, measure the packets.
Challenges · the edges of Tahoe

Living with a dormant upstream

The response

Carry small tested workarounds in our images · pin what upstream doesn't · route around dead frontends (web gateway, the NAS pattern) · document quirks where users hit them.

The insurance

Identity, membership and the mesh don't know the storage engine is Tahoe. The engine is swappable; the network is not.

I picked Tahoe knowing it moves slowly. The mitigation is architecture, not hope: identity, membership and the mesh don't know that the storage engine is Tahoe.

Security hardening from a 50-finding audit

Method: six auditors by dimension → adversarial verification of every finding → six batches ranked by blast radius, shipped as small releases. Then a second pass from the inside: what can a malicious member do? Relay DoS, address hijack, rogue storage servers. Ranked, partly fixed, the rest on the roadmap.

If someone asks why the manifest isn't signed: it was the biggest finding and I deferred it on purpose. Today the boundary is GitHub auth, branch protection and review. Signing would protect against a compromised GitHub account. Known gap, on the list. The insider pass is worth a sentence: a member cannot read anyone's data or forge an identity, because encryption is client-side and every Tahoe connection pins the server key. What a member can do is take the network down or quietly weaken it, and the fixes for that are one-liners in tinc and the census, plus Tahoe's grid-manager certificates for the rogue-server case.

Testing a distributed system on a laptop

What tests couldn't catch: the netns trap, the override drop, Compose v1 on a fresh OS. Environment semantics. Each became a unit test on the CLI's command construction, because that's where the bug lived. And the build itself was a bug: Tahoe's Rust dependency has no ARM wheels, so every release compiled it for an hour under emulation. Now a base image is rebuilt only when the lock changes, natively per architecture, and a release takes minutes.

Be honest about what the test pyramid doesn't cover: the hub image isn't built in CI yet. On the roadmap, not hidden.

Using it: a home NAS with an erasure-coded time machine

A member proposed this design; I had proposed the FUSE route. Theirs was better because it works with Tahoe's immutable model instead of against it. Say so. Optional demo: drop a file on the share, watch it appear in backups:Latest/.

Day-2 operations

# join: writes .env, exports the GPG key, prints the exact start command
redundanet network join --repo <manifest repo> --name node-303c084b

# safe self-update: detect via docker inspect, recreate tinc first, health-check, roll back
redundanet update --check
redundanet update

# files and the network
redundanet storage upload photo.jpg home:photo.jpg
redundanet storage ls backups:Latest/
redundanet storage quota      # my allocation vs what I use on the grid
redundanet network peers
redundanet validate manifests/manifest.yaml

Everything a node needs: /opt/redundanet/.env + one override file for the disk. Errors say what to run next.

Skip this one if running late, the demo already showed the CLI.

What's next (ranked by risk, not by fun)

The left column is what this year bought. The middle is ranked by risk: the mesh hardening items are one-liners that close what a malicious member could do. The right column is what changes the trust model rather than the code, and I would only start it if the network grows past people I know.

What I'd tell myself at the start

  • Run your own network from day one. Every serious bug came from the live fleet, then became a test.
  • Validation not on the live path is dead code.
  • Choose by threat model, then isolate the choice.
  • Claim what you run.
  • Make failure legible: the best fixes were error messages that say what to run next.
  • The topology can lie: measure the packets.
  • Communities design better than you do.
End on the last bullet: the reason to build a community-run network is that the community makes it better. It ties back to Cubbit. Validation line: a beautiful validate() nobody called protected nothing; a manifest typo reached a node in 11 minutes. Packets line: I believed the mesh was a mesh for months; one tcpdump on one node proved every byte went through the hub.
