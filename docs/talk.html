Project talk

RedundaNet

Distributed, encrypted, very redundant storage, run by a community of volunteers, not a company.

Tahoe-LAFS · Tinc mesh VPN · GPG identities · a Git repo as the source of truth · Docker Compose · Raspberry Pis and old PCs

redundanet.com · github.com/adefilippo83/redundanet

Start with the one-liner: a storage network you join by opening a pull request, where your files survive any machine dying and nobody hosting them can read them. Then straight into the Cubbit story.

Where it came from: an orphaned idea

Very distributed (commodity hardware behind home NATs) · very redundant (erasure coding) · membership as a social process.

I backed the Cubbit Kickstarter in 2019 and I still have the box. When they pivoted to enterprise object storage I didn't blame them, it was the right business call. But it left the idea I cared about with nobody carrying it. A network the members run themselves can't pivot away from them. That's the whole reason this exists.

Six principles

🔒

Nobody can read your data

Encryption happens on your device. Hosts store ciphertext.

💥

Any node may die

Erasure coding, configurable k-of-n.

🗂️

No central authority

Identity = your GPG key. Membership = a file in Git.

🏠

Commodity, behind NAT

Home routers, no port forwarding. A mesh VPN relays.

🤝

Vetted, not anonymous

Members are approved humans. Some rules are an honor system, and we say so.

🧘

Boring operations

One CLI, one compose stack, self-update with rollback, a status page.

Dwell on "vetted, not anonymous". This is the trust model everything else leans on: members are approved humans, so some enforcement can be honor-system (quotas, later) and that's a deliberate choice, not naivety.

Architecture

Walk it left to right: the repo is the source of truth and nodes sync it; the keyservers are the PKI; the hub relays NAT-to-NAT and runs the introducer. Every node runs the same stack on whatever hardware. Mention that the tinc container owns the network namespace and the Tahoe containers join it. I come back to this on the incidents slide.

Why Tahoe-LAFS: the trust boundary

IPFS

public, popularity-based persistence

Ceph / MinIO

great for a trusted cluster you own

Storj / Sia

a token market, not a social contract

The criterion was the threat model, not the feature list. Untrusted hosts means encryption has to happen in the client, and that is Tahoe's entire thesis. Be upfront that upstream moves slowly: I chose it knowing that.

Connectivity & identity: Tinc + GPG

Why full fingerprints: a short key id is just the last 8 or 16 hex characters of the hash, and Evil32 showed you can forge one in seconds. Earlier versions accepted short ids and matched by suffix, so an attacker could upload a colliding key and become a node. Now rejected everywhere. Why tinc and not WireGuard: WireGuard is a tunnel, I needed a mesh with relaying and one identity; tinc gives both, I pay in throughput I don't need.

Inside a node: one compose stack, roles as profiles

docker compose -p redundanet --profile storage --profile client up -d · the Tahoe containers join tinc's namespace: no port plumbing, and one trap I'll show you.

The shared network namespace is elegant and it set a trap. Don't explain it here, just plant it.

Open the status page. Point at the census: it's built from each storage node's list of opaque storage indexes, no filenames, no content, served only over the VPN. The hub intersects them, and caches the last inventory so an offline node doesn't blind the count. Check before the talk that the census says complete.

Redundancy that is measured, not assumed

Today the network runs 1-of-2 (mirror); the next step is 2-of-4: same cost, survives two nodes. The rebalancer converts old files automatically.

Own the honesty point: the docs used to say 3-of-10 while production ran 1-of-2. I fixed the docs to say what we actually run. Claim what you run. Encoding is baked into each file at upload, so changing the manifest needed a re-encoder loop: it reads k and n straight out of the capability string and re-uploads from the grid itself.
Live demo 2

Kill a node, keep the file

# node A (client): upload, note the hash
sha256sum talk.pdf
redundanet storage upload talk.pdf home:talk.pdf

# node B (storage): take it down
docker stop redundanet-tahoe-storage

# status page: one server fewer, census shows reduced availability
# node A: download still works from the remaining copy
redundanet storage download home:talk.pdf /tmp/back.pdf
sha256sum /tmp/back.pdf     # identical

docker start redundanet-tahoe-storage   # census returns to fully replicated
Have talk.pdf ready and the hash already noted. Stop the Pi's storage container, download from falcon, compare hashes. The client reconnects in seconds. Start the container again before moving on.
Challenges · production incidents

Fix the class, not the instance

The vanishing disk

An explicit -f compose.yml disables Docker's override auto-load; an update silently detached a 1TB disk. Fixed in the CLI, with a test asserting two -f flags.

Fresh-node breakage

The Pi image shipped Compose v1; a manifest typo broke a join for 11 minutes. Now: pinned Compose v2 verified at build time, and actionable errors instead of tracebacks.

If short on time, tell only the vanishing disk: the command looked right, but an explicit -f turns off Docker's auto-loading of the override file, so an update silently detached a 1TB disk. The data was fine on the disk, the node just couldn't see it. A twelve-line fix plus a test that asserts two -f flags.
Challenges · the edges of Tahoe

Living with a dormant upstream

The response

Carry small tested workarounds in our images · pin what upstream doesn't · route around dead frontends (web gateway, the NAS pattern) · document quirks where users hit them.

The insurance

Identity, membership and the mesh don't know the storage engine is Tahoe. The engine is swappable; the network is not.

I picked Tahoe knowing it moves slowly. The mitigation is architecture, not hope: identity, membership and the mesh don't know that the storage engine is Tahoe.

Security hardening from a 50-finding audit

Method: six auditors by dimension → adversarial verification of every finding → six batches ranked by blast radius, shipped as small releases.

If someone asks why the manifest isn't signed: it was the biggest finding and I deferred it on purpose. Today the boundary is GitHub auth, branch protection and review. Signing would protect against a compromised GitHub account. Known gap, on the list.

Testing a distributed system on a laptop

What tests couldn't catch: the netns trap, the override drop, Compose v1 on a fresh OS. Environment semantics. Each became a unit test on the CLI's command construction, because that's where the bug lived.

Be honest about what the test pyramid doesn't cover: the hub image isn't built in CI yet. On the roadmap, not hidden.

Using it: a home NAS with an erasure-coded time machine

A member proposed this design; I had proposed the FUSE route. Theirs was better because it works with Tahoe's immutable model instead of against it. Say so. Optional demo: drop a file on the share, watch it appear in backups:Latest/.

Day-2 operations

# join: writes .env, exports the GPG key, prints the exact start command
redundanet network join --repo <manifest repo> --name node-303c084b

# safe self-update: detect via docker inspect, recreate tinc first, health-check, roll back
redundanet update --check
redundanet update

# files and the network
redundanet storage upload photo.jpg home:photo.jpg
redundanet storage ls backups:Latest/
redundanet network peers
redundanet validate manifests/manifest.yaml

Everything a node needs: /opt/redundanet/.env + one override file for the disk. Errors say what to run next.

Skip this one if running late, the demo already showed the CLI.

What's next (ranked by risk, not by fun)

Lead with GC: silent data loss is the scariest item in any storage system. The rest is ranked by risk on purpose.

What I'd tell myself at the start

  • Run your own network from day one. Every serious bug came from the live fleet, then became a test.
  • Validation not on the live path is dead code.
  • Choose by threat model, then isolate the choice.
  • Claim what you run.
  • Make failure legible: the best fixes were error messages that say what to run next.
  • Communities design better than you do.
End on the last bullet: the reason to build a community-run network is that the community makes it better. It ties back to Cubbit. Validation line: a beautiful validate() nobody called protected nothing; a manifest typo reached a node in 11 minutes.
