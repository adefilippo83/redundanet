Project talk

RedundaNet

Distributed, encrypted, very redundant storage — run by a community of volunteers, not a company.

Tahoe-LAFS · Tinc mesh VPN · GPG identities · a Git repo as the source of truth · Docker Compose · Raspberry Pis and old PCs

redundanet.com · github.com/adefilippo83/redundanet

Open: one sentence — "I built a storage network you can join by opening a pull request, where your files survive any single machine dying and nobody who hosts them can read them." Then the origin story.

Where it came from: an orphaned idea

Cubbit, 2019 (Kickstarter)

  • A little box you plug in at home; your data is split, encrypted and spread across everyone's boxes
  • Storage as a peer-to-peer commons — I backed it and got the device
  • Then the company pivoted to enterprise object storage. Reasonable business call. The consumer commons idea was orphaned.

The part I didn't want to let go

  • A network maintained by volunteers, with no company in the middle that can pivot away
  • Very distributed: commodity hardware behind home NATs
  • Very redundant: erasure coding, not just mirroring
  • Membership as a social process — you join because people vouch for you
Point: the business pivot is not a criticism of Cubbit — it is the reason a community-owned version has to exist: nobody can pivot a network its members run themselves.

Design principles (and what they forced)

Nobody can read your data

Not the hosts, not the operator. Encryption must happen client-side; the storage layer sees only ciphertext shares.

Any node may die

Files survive a Raspberry Pi with a dead SD card. Erasure coding with configurable k-of-n; the network keeps working read-only even below threshold.

No central authority

No server that, if it disappears, takes membership with it. Identity = a GPG key you own; membership = a file in a Git repo anyone can fork.

Commodity, behind NAT

Home connections, no port forwarding required. A mesh VPN that relays NAT-to-NAT.

Vetted, not anonymous

Members are approved humans. That lets some enforcement be an honor system — a deliberate trade, stated openly.

Boring operations

One CLI, one docker compose stack, a self-updater that can't brick a node, a public status page.

Emphasize: "vetted, not anonymous" — this is the trust model that makes several later decisions (client-side quotas, keyserver PKI) defensible rather than naïve.

Architecture

Walk it: repo → nodes (manifest sync), keyservers → peer host files, hub relays + introduces, heterogeneous nodes running the same stack. Stress: "the VPN namespace is owned by the tinc container; the Tahoe containers join it" — this becomes a story later.

Why Tahoe-LAFS as the storage engine

  • Provider-independent security — encryption and integrity happen in the client; storage servers are untrusted by design. Exactly the volunteer-host threat model.
  • Capabilities — an unguessable URI is the access right. No ACL server, no accounts to run.
  • Erasure coding built in — k-of-n Reed-Solomon, "servers of happiness" placement guarantees.
  • Mature — since 2007, audited (Cure53), Python, runs on a Pi.

Alternatives I weighed

IPFS
content-addressed & public by default; no redundancy guarantee without pinning services
Ceph / MinIO
excellent — for a trusted cluster you own; wrong threat model for volunteer hosts
Storj / Sia
token economies; I wanted a social contract, not a market
Roll my own
the crypto and placement logic is precisely where I'd get it wrong

The cost of the choice: a dormant upstream. More on that later.

Interview-grade point: the selection criterion was the threat model, not features. Untrusted hosts ⇒ client-side crypto ⇒ Tahoe's whole design thesis.

Connectivity & identity: Tinc + GPG

Tinc mesh VPN

  • Full mesh with automatic relaying — two nodes behind NAT talk via the hub, direct when they can
  • Decentralized: every node holds every peer's public key (host files)
  • RSA keys → one identity for VPN and membership: the node's GPG key is converted (pgpy → PKCS#1 PEM) and used as the tinc key. No second keypair to manage or lose.

Membership pipeline

  • Applicant publishes a GPG key, submits the full 40-char fingerprint via a form → GitHub issue
  • Bot verifies the key is fetchable from keyservers and matches exactly — else the join fails closed
  • Bot opens a PR adding the node to the manifest; CI validates; a human merges
  • Every node's sidecar pulls the manifest and rebuilds its tinc host files → the mesh admits the newcomer within minutes

Git gives audit history, review, and revocation (delete the node, merge) for free.

Why full fingerprints: short key ids are brute-forceable (Evil32). Earlier versions accepted 8/16-char ids and matched by suffix — an attacker could upload a colliding key. Now rejected everywhere. Good "I found and closed a hole" story.

Deployment: one compose stack, three roles

# profiles select what a node runs
docker compose -p redundanet --env-file /opt/redundanet/.env \
  --profile storage --profile client up -d

# the tahoe containers live inside tinc's network namespace
tahoe-storage:
  network_mode: "service:tinc"
  depends_on: { tinc: { condition: service_healthy } }
  volumes: [ /mnt/storage/redundanet:/data/storage ]
  • Roles = compose profiles: introducer, storage, client — derived from the manifest at join time
  • Shared netns: Tahoe binds on the VPN IP without any port plumbing; tinc owns the namespace
  • Hub on fly.io: Firecracker microVM, dedicated IPv4, a volume for the introducer's identity
  • Prebuilt Raspberry Pi image (Trixie, pinned Compose v2) built in CI under QEMU
  • A CLI (redundanet) wraps it all: join, update, storage, sftp, validate
Foreshadow: "shared netns is elegant and it set a trap I'll show you."

Redundancy that is measured, not assumed

Erasure coding, configurable per network

  • shares_needed / shares_happy / shares_total live in the manifest
  • Today: 1-of-2 mirror, happy=2 — every object on two distinct servers. Small network, honest parameters.
  • Growth policy: raise to e.g. 2-of-4 when the fleet reaches ~4–5 nodes (a manifest PR)
  • redundanet validate warns when happy == node count — no write headroom (lose one node ⇒ read-only)

Verified by failure drill (and in CI)

  • Production: stopped a storage node, downloaded via the other, byte-identical
  • CI grid test: 3 storage nodes, 2-of-3, upload → kill a node → download → sha256 match, every push
  • The census turned an assumption ("it's replicated") into a number I watch
Honesty beat: docs used to say "3-of-10" while production ran 1-of-2. I reconciled the docs to "configurable k-of-n" — claim what you run.
Live demo 2

Kill a node, keep the file

# on node A (client): upload, note the hash
sha256sum talk.pdf
redundanet storage upload talk.pdf home:talk.pdf

# on node B (storage): take it down
docker stop redundanet-tahoe-storage

# status page: 1 storage server connected, census incomplete
# on node A: download still works from the remaining copy
redundanet storage download home:talk.pdf /tmp/back.pdf
sha256sum /tmp/back.pdf     # identical

# bring B back; the census returns to fully replicated
docker start redundanet-tahoe-storage

Plain docker stop/start is safe for a tahoe container — it re-joins tinc's live namespace. (Restarting tinc itself is a different story — next.)

Timing: the client reconnects to remaining servers within seconds; the download uses the surviving share. Prepare the file beforehand so the upload is instant.
Challenges · production incidents

Fix the class, not the instance

The netns trap

Recreating the tinc container gives it a new network namespace; the Tahoe containers stay attached to the dead one — "0 shares connected". Fix: redundanet update always force-recreates tinc first and the Tahoe services with it; documented as a rule.

The vanishing disk

The CLI passed -f docker-compose.yml, which disables Docker's auto-loading of the override file holding the storage bind-mount. An update silently detached a 1TB disk: the node "lost" all objects (they were fine on disk). Fix: the CLI now includes the override explicitly, with a test.

Fresh-node breakage

The Pi image shipped Debian's docker-compose (v1, 2021); the CLI needs v2. A hand-edited manifest with a typo broke a node's join for 11 minutes. Fixes: pinned Compose v2 plugin verified at image-build time; the CLI diagnoses bad YAML instead of a traceback.

Each one became: a test, a CLI guard, and a doc line — the incident can't recur the same way.

Pick one to tell fully: the vanishing disk is the best — a correct-looking command with a subtle Docker semantic (explicit -f disables override auto-load). The fix is 12 lines and a test that asserts two -f flags.
Challenges · the edges of Tahoe

Living with a dormant upstream

  • Last release: 1.20.0, Dec 2024. The SFTP frontend hasn't seen functional work since 2023.
  • SFTP never closes sessions — the server consumes the client's disconnect and keeps the TCP connection forever; exit hangs. Bisected: not the client (OpenSSH 9.6 & 10.2), not the network (loopback), not Twisted (23 & 25). It's upstream code nobody maintains.
  • No accounting — a storage server can't tell who uploaded what. Per-client quotas can only be client-enforced (fine under a vetted-member trust model; stated honestly).
  • Unpinned transitive deps — pyOpenSSL 25 removed an API; every Tahoe container crash-looped. Caught by the grid e2e test; pinned.

The response

  • Carry small, tested workarounds in our images; pin what upstream doesn't
  • Route around dead frontends: Tahoe's web gateway is the maintained one; the NAS pattern avoids SFTP entirely
  • Document quirks where users will hit them, not in a changelog
  • Keep the storage engine swappable in the architecture: the manifest, identity and mesh don't know it's Tahoe
Judgment call to highlight: I chose Tahoe knowing it's slow-moving; the mitigation is architectural isolation, not hope.

Security hardening from a 50-finding audit

Trust boundary on the source of truth

  • Full 40-char fingerprints only; exact match; suffix matching removed (Evil32)
  • Joins fail closed: key must be fetchable and match, or no PR
  • Publishing gated on green CI — :latest and PyPI can't ship a red commit to a fleet that auto-pulls
  • validate exits non-zero on real errors; advisory warnings stay warnings

Safe self-update

  • redundanet update: detects new images via docker inspect (not compose images, which returns nothing on some versions)
  • Captures the running image IDs, recreates (tinc first), health-checks, and rolls back to the previous images if the node doesn't recover
  • Never blanks a node's key or wipes operator settings on re-join (.env is merged, not overwritten)

Method: six auditors by dimension → adversarial verification of every finding → prioritized batches. Shipped as small, tested releases (2.7.5 → 2.7.11).

If asked "how did you audit it": multi-agent read of the whole codebase by dimension, each finding independently re-verified against the code before it made the list, then six batches ranked by blast radius (publish safety first).

What the grid test proves, every push

Introducer + 3 storage nodes + client in compose; upload with 2-of-3; assert shares landed on 3 distinct hosts; stop one; download; sha256 equal. It caught the pyOpenSSL breakage before any node did.

What tests couldn't catch

The netns trap, the override-drop, compose v1 on a fresh OS — environment semantics. Each is now a unit test on the CLI's command construction, because that's where the bug actually lived.

Mature framing: know what your test pyramid doesn't cover; the gaps that remain (container entrypoints, hub image not built in CI) are on the roadmap, not hidden.

Using it: a home NAS with an erasure-coded time machine

First instinct: mount the grid via FUSE (sshfs) and re-export over Samba. Wrong tool:

  • Tahoe files are immutable → every edit re-uploads the whole file
  • Finder/Windows write noise (temp files, partial writes) hammers the grid
  • "Saved" reported before the upload finishes

Better: local share, async one-way sync.

LAN ──SMB──▶ Samba share on the node (real disk)
                     │  read-only bind-mount
                     ▼
          tahoe backup, every 15 min, incremental
                     ▼
   grid: backups:Archives/<timestamp>/  +  backups:Latest/

# .env on the node
SYNC_ENABLED=true
SYNC_DIR=/mnt/storage/share

Snapshots accumulate on purpose — that's the oops/ransomware protection. Restore from any node. (Optional demo: drop a file on the share, watch it appear in backups:Latest/.)

Design story: a user proposed this; I had proposed the FUSE route. Theirs was better because it plays to Tahoe's immutable model instead of fighting it. Say that — it shows you take good ideas from anywhere.

What's next (ranked by risk, not by fun)

Redundancy promises

  • GC vs. lease renewal: storage expires unrenewed shares after 90 days; make expiry opt-in or renew fleet-wide
  • Introducer SPOF: the hub is the only rendezvous point; support Tahoe's multi-introducer list
  • Quotas: hard per-node caps from storage_contribution; client-enforced storage_allocation with usage on the status page
  • Disk setup tooling for the Pi (mount + fstab + override) — today it's a documented procedure

Engineering hygiene

  • Unit-test the container entrypoints (the historical blind spot); build the hub image in CI
  • Nightly e2e runs to catch environment drift between commits
  • Browser access via Tahoe's web gateway (the maintained frontend) instead of SFTP
  • Alerting on status.json: node down, servers < shares_needed, census incomplete
  • Input hardening leftovers: SFTP usernames, node names in file paths
Signal: you know the difference between what's shiny and what's risky. Lead with GC — silent data loss is the scariest item in any storage system.

What I'd tell myself at the start

  • Run your own network from day one. Every serious bug was found by the live fleet, not by tests — then turned into a test.
  • Validation that isn't on the live path is dead code. A beautiful validate() nobody calls protected nothing; a manifest typo reached a node in 11 minutes.
  • Choose by threat model, then isolate the choice. Tahoe was right for untrusted hosts; keeping identity, membership and mesh engine-agnostic is what makes its dormancy survivable.
  • Claim what you run. "3-of-10" in the docs vs 1-of-2 in production erodes exactly the trust a storage system lives on.
  • Make failure legible. The best fixes this year were error messages that say what to run next.
  • Communities design better than you do. The NAS sync architecture came from a member; the join pipeline exists because a friend wanted in.
Close on the last bullet — it ties back to the origin: the reason to build a community-run network is that the community makes it better.
