Migrate from RedundaNet 2

For members of the old grid. Six steps, at your own pace. Nothing on your RedundaNet 2 node changes until the last one, and that one has a rollback.

On this page

  • 1. Identity on your laptop
  • 2. The legacy attestation
  • 3. The join request
  • 4. The agent on each node
  • 5. Native backup sets and a restore test
  • 6. Retire the Docker stack
RedundaNet 3 runs beside your RedundaNet 2 stack. The old grid stays live until a stop date the maintainer announces, because its Tahoe shares still hold members' data. On a RedundaNet 2 node both tools exist: the Python redundanet on PATH is the legacy one, and the Go agent lives at /var/lib/redundanet3/bin/redundanet. Every command on a node below uses the full path. The long form is docs/migration.md on GitHub.

1. Identity on your laptop

Only the laptop ever holds your phrase. Install the agent there with one line; the page it opens makes a new identity, shows your member key and links to the join form (redundanet setup does the same in a terminal); the network is built into the binary, nothing to join by hand.

curl -fsSL https://redundanet.com/install.sh | sh

2. The legacy attestation

Your RedundaNet 2 nodes are listed with GPG keys. Sign your new member key with one of them; that ties the new identity to the person the network already trusts. If the key lives on the node, run the command there.

printf '%s' <member key> | gpg --armor --detach-sign -u <fingerprint of one of your nodes' keys>

Keep the armored output and the 40-character fingerprint you signed with: both go into the join request.

3. The join request

Fill the join form with your member name, your member key, the disk you contribute, and, in the RedundaNet 2 section, the fingerprint and the signature. If you contribute disk, the form also wants your node's device key, which step 4 prints; most members do step 4 first and send one request.

A workflow validates the request and opens a pull request; the maintainer signs the manifest offline and merges; every agent applies it within five minutes.

4. The agent on each node

The storage node flow: one line as root on the node lays the agent out as a system service and shows a pairing code; your laptop, on the node's network or anywhere (the hub relays the exchange), certifies it through the code, and the node joins and starts by itself. The agent runs beside the Docker stack on the host's network and stores shares under STORAGE_PATH/redundanet3. For a node your laptop cannot reach, the runbook's certificate file over SSH does the same.

# on the node, as root, with the storage disk mounted
curl -fsSL https://redundanet.com/install.sh | sudo sh -s -- --node /mnt/storage

# on your laptop, with the phrase
redundanet device pair --storage <code>

The runbook: agent/deploy/node/README.md. The node appears on the status page under your name once the manifest lists it.

5. Native backup sets and a restore test

Add a native backup set for every folder that backup-sync pushed to the old grid, on the device that holds the folder. The agent scans it daily and runs a restore test weekly.

# on a node
sudo /var/lib/redundanet3/bin/redundanet backup add NAME FOLDER [FOLDER...]
sudo /var/lib/redundanet3/bin/redundanet backup run NAME
sudo /var/lib/redundanet3/bin/redundanet backup verify      # a restore test now
sudo /var/lib/redundanet3/bin/redundanet backup list        # sets, runs and restore tests

Go on to step 6 only with a passed restore test on the native grid, listed by backup list and on the local page.

6. Retire the Docker stack

Not before the stop date is announced. A node's Tahoe shares hold other members' data too, and the old grid is 2-of-4. The wind-down is manual: no countdown and no automatic deletion exist.

migrate-node stops and removes the containers, whole, tinc first; files and shares stay on disk. It refuses while anything is missing from the native grid. Dry run first; --rollback brings every service back together.

sudo /var/lib/redundanet3/bin/redundanet migrate-node --dry-run    # the plan, and what is not yet on the native grid
sudo /var/lib/redundanet3/bin/redundanet migrate-node              # retire the stack
sudo /var/lib/redundanet3/bin/redundanet migrate-node --rollback   # every service again, tinc first
sudo /var/lib/redundanet3/bin/redundanet migrate-node --force      # past a refusal, on purpose

The agent keeps running through all of it and the node stays on the status page. A drill is migrate-node followed by --rollback within a few minutes, inside the old grid's tolerance of two servers down.
