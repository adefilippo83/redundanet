# Security

A short version of the security section of [RFC 0001](../rfcs/0001-redundanet-3.md). What the software sends and to whom is in [../PRIVACY.md](../PRIVACY.md). Anonymity is not a goal: a network observer learns who talks to whom and how much.

## Keys and the phrase

A member is a 128-bit seed, shown once as a 12-word phrase by `redundanet identity init`. Everything else is derived from it or certified by it:

| Key | Used for | Lives where |
| --- | --- | --- |
| Member signing key (Ed25519) | Certifies devices, revokes devices, signs the join request | Nowhere at rest: derived from the phrase when needed, then erased |
| Member secret | Derives the per-object encryption keys and the key that seals root records | Every device of the member, in the identity file |
| Device key (Ed25519) | Transport identity on the mesh; signs every storage request, descriptor, delete token and the device's own root | That device only |
| Device certificate | Proves to servers and peers that the device acts for a listed member | Presented on connect; stored by servers beside what the device wrote |

The split is the point: everything a device does every day is signed by its own key, so taking a device gives an attacker that device and nothing more. Certifying and revoking need the phrase in hand.

The phrase appears only on the device itself: in the CLI or in the local page on `127.0.0.1`, and on a headless node through SSH. Nothing on the network ever asks for it; the weekly restore test never asks for it. There is no phrase check command in 3.0.0 and no OS keystore: the identity file is sealed with a passphrase when you ask for one (`--passphrase`), otherwise the file mode is its protection, as on a headless node.

## What is encrypted, and by whom

Each file is split into objects. Each object is encrypted on your device with a key derived from your member secret and the object's own content (AES-256-GCM per segment), erasure coded into shares, and only shares go to storage servers, each with a descriptor signed by your device. File names, folder structure and the snapshot index are themselves stored inside encrypted objects. A storage server, and the hub, learn that your member stores an object of a given size at a given time, and how much you store in all. They cannot read names or contents, alter a share undetected, forge a share's owner or inflate another member's usage. Every read verifies the hash tree before a byte is written. A server cannot make a backup skip an upload by saying the object is there already: the device asks for the descriptor it signed itself, which exists only for an object that was uploaded, and counts each server for no more shares than placement gives one server. A server cannot roll your snapshot list back either: a device remembers the last root it confirmed and does not build a backup or a cleanup on an older one. And what a descriptor may claim about an object's size is bounded, so a member cannot make a server spend its time on an object that could not exist. A server cannot stop your backups by overstating what it holds for you either: your device counts each server's answer up to the limit the manifest gives that server for you and no further. On a network where one server is half the storage or more, that limit alone can reach your allocation. A server that did hold a share can still say it holds it after losing it; the share census, repair and the restore test are what catch that. What a server tells the hub in its census is its own word too: one server reporting an object as deleted, or reporting it under another descriptor, does not take it out of repair; that needs most of the servers concerned.

Devices talk over QUIC with TLS 1.3, authenticated by their device keys. A relayed connection goes through the hub as ciphertext the hub cannot read.

## What the hub sees, and cannot do

The hub introduces devices to each other, relays traffic when no direct path exists, collects the census and publishes the status page. It sees device keys, IP addresses, liveness, the share census (storage indexes, owners, sizes, encodings) and relayed volumes. A compromised hub can drop or delay traffic, publish a false page, hand out wrong addresses (after which connections fail rather than being misdirected), serve a stale manifest within its maximum age, and issue repair tasks that place surplus copies of real objects. It cannot admit a member, forge a manifest, a revocation or a release, read a share, impersonate a device or delete an object. The one thing it can ask a server to remove is a surplus copy of a share, and the server decides: it asks the other holders itself and gives its copy up only when every share number stays accounted for, counting each other holder for no more shares than placement gives one server. A hub working together with a dishonest storage server can therefore cost an object no more than the shares that server was trusted with in the first place, which the encoding is chosen to survive. For the rest: manifests, revocations and releases carry signatures by keys the hub does not hold, revision numbers stop rollback, and devices authenticate each other end to end. Nothing on the hub is needed to recover any member's data.

The live network has one hub, on a bare IP address. With it down: no new connections, no repair scheduling, no status page; existing direct connections continue.

## The manifest and the repository

Agents apply only a manifest signed by an operator key pinned when the device joined, with a revision above the last one applied. The keys come from the network descriptor built into the binary, which the signed release index vouches for, and a device that never joined by hand follows that descriptor across releases; a descriptor given to `network join` is pinned until the next one. A compromised repository account can change files on main and delay changes, but cannot admit a member, change k-of-n, install a binary or read data. A stolen operator key can sign a manifest, so it could admit a member or change allocations; it cannot install a binary, read data, or delete anything inside the grace period, which every server measures on its own clock. Recovery from a stolen operator key is a new network descriptor: built into the next release for the devices on the built-in network, sent out of band to a device that joined by hand. Releases are signed with a separate offline key that CI never holds; the index can withdraw a version. The public half of that key is written in the source (`agent/internal/version`), not taken from a setting of the build service, and before signing a release the maintainer builds it again from the tagged source on the laptop that holds the key and signs only when every binary on the release equals the one built there. So the signature says which source a binary was built from, and a binary that the build service altered is not signed. The limits: the comparison is with a build on one laptop, with the Go toolchain as downloaded and checked against Go's checksum database, and a binary that is code signed after the build (none is today) cannot be compared this way. A first install from the one-line installer trusts GitHub and the website until the installed binary has checked the index.

## Device revocation

A new device is certified either by typing the phrase on it, or by pairing: the new device shows a one-time code with a 160-bit secret and its own device key, an existing device with the phrase connects to it and hands over the certificate and the member secret. The two first agree on a one-time key (X25519), and everything after is sealed under a key made from that agreement and the code's secret, so each exchange has a key of its own and a hub that relays one cannot replay or alter it in another. The new device signs the agreement with its device key, and the existing device checks that against the key in the code before it sends anything: someone else who has read the code cannot receive the member secret in the new device's place. Whoever is between the two sees only ciphertext; a wrong code opens nothing and three failed connections end the code. The member secret travels, as it does in a certificate file; the phrase does not. What the code still is: a way to answer the new device. Whoever holds it before you use it can hand that device an identity of their own, so it is for your eyes until the pairing is done; `device pair` asks for it instead of taking it on the command line, and you see on the existing device whether the pairing was yours. A code from a device on a version before 3.0.15 does not name a key and pairs by the earlier exchange, sealed under the code alone.

A member revokes a lost or stolen device from any other device of theirs with `redundanet device revoke --device KEY`: the command asks for the phrase, signs a revocation record, and the running agent applies it at once and sends it to every storage server and every hub, which spread it to every device within seconds and to any device that connects later. The command also prints the record; the operator adds it to the manifest under `revocations:`, signs and merges, so it survives every later manifest and reaches whoever was unreachable. What the device wrote while it was trusted keeps verifying, so repair keeps working.

## What a lost device can do

Until it is revoked, the holder of your device can read everything your devices can read (the device holds the member secret), and write and delete as that device. It cannot certify a device, revoke your other devices, write another device's root, or act after revocation. Deletion is two-phase: anything it deletes stays recoverable for 30 days from any other device of yours, and nothing it deletes can be purged within that window. A stolen phrase is a different matter: it is a new identity, and the operator retires the old one. Snapshots that device published before it was revoked stay in the restore list, and they are whatever its holder wrote. Restoring one writes only inside the folder you choose, whatever names and links the snapshot carries; check what such a snapshot contains before you use it.

## Losing the phrase

The data is unreadable to everyone, by design; there is no escrow and nobody can recover the phrase for you. `identity init` asks for three of the words back before writing anything. A member who loses the phrase starts over as a new member entry; what the old identity stored stays encrypted on the grid until the operator retires it and the grace period runs out.

## The local page and the browser

The agent serves its API and page on `127.0.0.1:4470` only, never on the LAN. A web page you visit could post to `127.0.0.1`, so: `redundanet open` prints a one-time link that works for two minutes and sets an HttpOnly, SameSite=Strict session cookie; every change carries a CSRF token; the API answers only requests whose Host is loopback and, for changes, whose Origin is the page itself; no GET changes anything. The page's content policy lets the browser load one stylesheet and one script, both served by the agent itself, and nothing inline or from another origin; the script only refreshes the page's status from the agent and sends the language menu. The page takes the recovery phrase in two places: the setup wizard, when an existing member puts a new device in place from the phrase, and the "Add a device" form, which certifies a new device. It travels from the browser to the agent over loopback in the form's body, is used for that one certificate, and is not stored, logged or shown back; the agent refuses a phrase that is not this device's member's. What can read it there is what can read the browser: an extension with access to pages on `127.0.0.1`, or malware on the machine. `redundanet device pair` in a terminal keeps it out of the browser. Another user or process on the same machine can connect to the port but needs the bearer token, kept in a file only the agent's user can read. A headless node is reached over an SSH tunnel.

## Self-update

The agent checks the signed release index hourly, installs only what the index names after verifying hash and size, runs the candidate in probation for up to two minutes, keeps the old binary as `redundanet.old` and rolls back on its own. The release key rotates only through records in the index signed by the key being retired, so an old binary still verifies a newer index. Binaries themselves are unsigned at 3.0.0 (Windows signing and macOS notarization are set up in the workflow, not yet active); the index is the verification on every platform.

## Reporting

Report a security problem to the maintainer through the repository; for a problem on your own device, `redundanet diagnostics` writes a bundle which you send by hand. Before anything is written to it, each path is replaced by a short hash and each URL and address by a mark; a path is taken whole, spaces included, up to the reason of the error it stands in, and the folders of your backup sets, the data folder and your home folder are replaced wherever they still appear. This works by pattern, not by knowing what is private: a name that stands in a line in no form the patterns know stays, so look through `log.txt` in the zip before you send it. Nothing is uploaded automatically.
