RedundaNet 3.0.0

One static binary, identity from a phrase, backups erasure coded across members, weekly restore tests, repair without the owner, self-update with rollback.

6 November 2026 · All news

RedundaNet 3.0.0 is released today from the tag agent/v3.0.0, on the stable channel. Twenty-four alpha builds on the early channel came before it, each one rolled to the live hub and nodes by the agent's own self-update.

What it is

RedundaNet is community-run encrypted backup. Each member runs the agent on their devices. A backup set is one or more folders; the agent scans them daily, encrypts every object on the device with a key derived from the member's secret and the content, splits it with erasure coding, today 2-of-3 on the live network, and places the shares on other members' storage servers. Nobody else can read the data, not the hub, not other members. A weekly restore test reads a sample back and compares it to the source. Storage servers scrub their shares monthly, and the hub schedules repair of under-placed objects without involving the owner. Deleted data stays recoverable for 30 days.

It is one static binary named redundanet, written in Go. No containers, no Python, no Docker. Builds for Linux (x86-64 and ARM64), macOS (Apple silicon and Intel) and Windows are on the download page, each listed with its sha256 in the signed release index.

What changed for members

  • Identity. A member key comes from a twelve-word phrase shown once at redundanet identity init. Every device gets a certificate signed by the member key. No GPG keys on keyservers.
  • Membership. Member and storage lists live in a manifest in the repository, signed offline by the maintainer's operator key. Agents fetch it every five minutes and apply a newer signed revision at once. Joining is a form that opens a GitHub issue; a workflow validates it and opens the pull request.
  • Network. No VPN. The agent reaches the hub outbound; devices connect directly through hole punching when they can, otherwise through the hub's relay, over QUIC with TLS 1.3. No inbound firewall rule is needed.
  • Backups. Native backup sets, daily runs, snapshots under a retention policy, restores per file, folder or snapshot, and a weekly restore test whose streak shows on the status page.
  • Updates. The agent checks the signed release index hourly, verifies the hash, runs the new version in probation for up to two minutes, keeps the old binary as redundanet.old, and rolls back by itself if the new one does not reconnect.
  • Lost devices. redundanet device revoke --device KEY on any device of the member prints a signed revocation record for the manifest; once the operator signs and merges, every agent and server refuses that device.
  • Diagnostics. redundanet diagnostics writes a bundle with no paths, URLs or addresses, to send by hand. Nothing is ever uploaded automatically. The privacy policy lists every exchange the software makes.

Platforms

Tested on Linux (x86-64 and ARM64, including Raspberry Pi 5) and Apple silicon Macs. Windows and Intel Mac builds are provided and pass the test suite, but have not run on the live network yet.

Windows signing through SignPath and macOS notarization are set up in the release workflow but not yet active (accounts pending); until then every binary is unsigned and the signed release index is the way to verify a download on every platform. Linux binaries are never code-signed; the index covers them.

What is not there yet

  • One hub, on a bare IP address. With it down there are no new connections, no repair scheduling and no status page; existing direct connections continue. The public status page is hosted on the fly.io app of the old product.
  • No bandwidth caps yet.
  • No settings page: the retention policy is edited in backup.yaml by hand.
  • No phrase check command.
  • No device pairing: each device is certified from the phrase.
  • No OS keystore.
  • Windows and Intel Mac untested on the live network. Raspberry Pi 4 not measured.
  • Quota is enforced server-side as a bound with headroom; the exact budget is the client's.
  • The RedundaNet 2 wind-down is manual.
  • Device revocation travels through the signed manifest, which the maintainer merges, so it takes effect when the maintainer signs, not within seconds.

RedundaNet 2

The old grid, the Python CLI with Docker Compose, tinc and Tahoe-LAFS, stays live until a stop date the maintainer announces, because its Tahoe shares still hold members' data. Six members and eight storage nodes are on it today; one member and two nodes also run RedundaNet 3. Existing members migrate at their own pace: identity on the laptop, the join request with the legacy GPG attestation, the agent on each node, native backup sets for the folders the old grid held, a passed restore test, then migrate-node retires the Docker stack, with a dry run first and a rollback. The migration guide has the steps; the old documentation is under docs/legacy.
